01 — The Identity Problem
Five Source Systems, Four ID Formats

Every system was built by a different vendor. Each refers to the same three physical sites using a different identifier convention. No system shares a key with another — making cross-system joins impossible without a semantic bridge.

The Problem

A question like "What is the labour cost per meal served at London Canary Wharf?" requires joining EPOS (SITE-LDN-01) with Infor WFM (GBR_SITE_0001). Without a semantic bridge, the join silently returns 0 rows. Every cross-system KPI has this problem.

03 — Technical Approach
Local Proof of Concept → AWS Production Equivalent

Every layer of the local stack has a direct AWS analogue. The architecture validates the approach locally using open-source tools; migration to AWS replaces each component like-for-like without changing the semantic model.

Stage ▲ AWS Equivalent
Data Storage DuckDB in-process analytical DB (hospitality.duckdb). Single file, no server. 5 tables, ~2,700 rows. Amazon Redshift Serverless or S3 + AWS Glue Data Catalog. Each source system maps to a schema/database in the catalog.
Schema Discovery generate_ontology.py introspects DuckDB with DESCRIBE — reads column names, types, row counts for all 5 tables. AWS Glue Crawlers automatically discover schemas from S3, RDS, or JDBC sources. Results are registered in AWS Glue Data Catalog.
Ontology Construction rdflib (Python). Explicit OWL Turtle handcrafted from schema introspection: 8 classes, 17 properties, 3 site individuals each with 4 ID bridge properties. AWS Context Ontology Accelerator (COA) MODEL layer. Uses Bedrock embeddings to auto-generate semantic relationships. Equivalent to ~148 OWL triples at schema scale.
Identity Resolution SPARQL query on rdflib in-memory graph. One call resolves all 4 site ID formats. Returns: {epos_id, infor_code, sap_cc, sf_org, site_name}. Without this, every cross-system query returns 0 rows — silently. AWS COA Virtual Knowledge Graph (VKG) powered by Ontop/SPARQL. Same SPARQL syntax; execution backed by Redshift. Scales to millions of entities across all markets.
Cross-System Joins Python metric layer. SPARQL resolves IDs first; DuckDB executes per-system SQL queries using the resolved IDs. No hardcoded joins between systems. AWS COA Tier-2 agentic SQL. Resolved IDs are injected into Redshift SQL. Athena federated queries handle multi-source joins across S3/RDS/Redshift.
Metric Definitions Python functions in metric_layer.py. 5 governed metrics: labour cost per cover, revenue by category, food margin, SAP revenue per cover, SF headcount by contract. Amazon DataZone metric contracts + AWS COA Business Semantic Layer (BSL). Metrics published as versioned data products. Governed via DataZone catalog policies.
LLM Agent Ollama qwen2.5 (local). OpenAI-compatible tool-calling API. System prompt with 5 governed tools. Max 15 turns. Amazon Bedrock (Claude Sonnet 4.5 or Nova Pro). Bedrock Agents with action groups mapped 1:1 to the metric tools. Fully managed agent loop.
Dashboard / API FastAPI + uvicorn (dashboard_server.py). Endpoints: /api/ask (LLM path), /api/metric (direct). Embedded Chart.js frontend. Amazon API Gateway + AWS Lambda (Python). CloudFront serves the React/Chart.js frontend. QuickSight Q for embedded NL analytics dashboards.
Ontology Storage OWL Turtle file (hospitality_ontology.ttl) loaded into rdflib at startup. Re-generated on schema change. Amazon Neptune (RDF store) or AWS COA knowledge graph store. Triples persisted, versioned, and queryable via SPARQL endpoint without in-memory reload.
Governance & Lineage Tool call logs in agent output. SPARQL resolution logged per metric call. Source system attribution per data row. Amazon DataZone data lineage + AWS Glue Data Quality. Full column-level lineage from source → metric → dashboard. Auto-tracked in the DataZone catalog.

Identity Resolution SPARQL

PREFIX hosp: <http://hospitality.example.org/ontology#>
SELECT ?epos_id ?infor_code ?sap_cc ?sf_org ?site_name
WHERE {
  ?site hosp:eposSiteId    ?epos_id ;
        hosp:inforSiteCode ?infor_code ;
        hosp:sapCostCenter ?sap_cc ;
        hosp:sfOrgUnitId   ?sf_org ;
        hosp:siteName      ?site_name .
  FILTER(?epos_id = "SITE-LDN-01")
}
→ infor="GBR_SITE_0001" sap="CC-GBR-001" sf="OU-GBR-001"

What is the Identity Resolution Stage?

It is the step where you answer: "What is the same real-world thing called in each source system?" Every enterprise system names the same physical entity differently — built by a different vendor, at a different time, with no shared key design. Without resolving these, a JOIN across any two systems returns 0 rows, silently. There is no error; the query just finds no match.

Oracle MICROS EPOS
SITE-LDN-01
Infor WFM
GBR_SITE_0001
SAP S/4HANA
CC-GBR-001
SAP SuccessFactors
OU-GBR-001

Identity resolution builds a canonical reference — one authoritative record per real-world entity — and attaches all system-specific IDs as OWL properties. One SPARQL query against that record returns all four IDs at once. DuckDB then queries each system using the ID format that system actually understands.

In the pipeline this runs before any analytical query. It is a prerequisite, not an optimisation — skip it and multi-system metrics do not exist. On AWS, the same stage is delivered by the COA Virtual Knowledge Graph (VKG) — built by the MODEL layer using Bedrock embeddings, exposed as a SPARQL endpoint via Ontop on Amazon Neptune. Same query; automated construction rather than hand-coded.

Key Proof — Without the Ontology

Running SELECT SUM(labour_cost_gbp) FROM wfm_shifts WHERE site_id = 'SITE-LDN-01' returns 0 rows — the correct Infor WFM ID is GBR_SITE_0001. Similarly, sap_sales WHERE cost_center_code = 'SITE-LDN-01' returns 0 rows — SAP expects CC-GBR-001. Every cross-system metric fails silently without SPARQL resolution. This is the entire point of the ontology layer.
